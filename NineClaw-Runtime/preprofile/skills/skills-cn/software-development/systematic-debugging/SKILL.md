# 系统化调试

## 概述

随机尝试修复既浪费时间，又会引入新的 bug。快速打补丁只会掩盖底层问题。

**核心原则：** 尝试任何修复之前，务必先找到 root cause。只修复症状就是失败。

**违背这套流程的具体规则，就是违背调试的根本精神。**

## 铁律

```
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

如果尚未完成阶段 1，就不能提出修复方案。

## 反馈循环规则

反馈循环本身就是调试工作。在阅读代码、建立理论之前，先创建或确定一条**紧凑**命令：它能针对用户的确切症状变红，并在 bug 修复后变绿。紧凑循环必须快速、确定、可由 agent 执行，而且足够具体，确实能捕获这个 bug——而不仅仅是“没有崩溃”。

如果难以得到干净的复现，就应投入格外多的精力来构建这个循环。没有可变红循环就凭猜测行事，正是本技能旨在防止的失败模式。

## 何时使用

适用于**任何**技术问题：
- 测试失败
- 生产环境中的 bug
- 非预期行为
- 性能问题
- 构建失败
- 集成问题

**尤其要在以下情况使用：**
- 面临时间压力（紧急情况容易诱使人猜测）
- “只做一个快速修复”看起来显而易见
- 已经尝试过多种修复
- 上一次修复没有奏效
- 尚未完全理解问题

**以下情况也不要跳过：**
- 问题看起来很简单（简单 bug 同样有 root cause）
- 正在赶时间（仓促行事必然导致返工）
- 有人要求立刻修好（系统化处理比反复乱试更快）

## 四个阶段

进入下一阶段之前，必须完成当前阶段。

---

## 阶段 1：Root Cause 调查

**尝试任何修复之前：**

### 1. 仔细阅读错误消息

- 不要跳过错误或警告
- 其中往往包含确切的解决办法
- 完整阅读 stack trace
- 记下行号、文件路径和错误码

**操作：** 对相关源文件使用 `read_file`。使用 `search_files` 在代码库中查找错误字符串。

### 2. 构建紧凑的反馈循环

- 能否用一条命令触发用户的确切症状？
- 这条命令是否会因该 bug 而失败，并且只有在 bug 修复后才通过？
- 它是否足够快，可以反复运行？
- 它是否具有确定性？对于 flaky bug，能否把复现率提高到足以调试的程度？
- 如果无法复现 → 收集更多数据，不要猜测。

**构建循环的方法——大致按以下顺序尝试：**

1. 在能够触达 bug 的边界处编写**失败测试**：单元测试、集成测试或端到端测试。
2. 针对正在运行的开发服务器使用 **HTTP 脚本 / curl**。
3. 使用 fixture 输入进行 **CLI 调用**，并将 stdout/stderr 与预期输出做 diff。
4. 使用**无头浏览器脚本**（Playwright/Puppeteer），对 DOM、console 或 network 作断言。
5. **重放捕获的 trace**：HAR、请求 payload、事件日志、队列消息或 webhook body。
6. 编写**一次性 harness**，启动系统中最小但有用的部分，并调用失败路径。
7. 当 bug 表现为广泛输入空间中间歇出现的错误输出时，使用 **property / fuzz 循环**。
8. 当 bug 出现在两个已知状态之间时，使用适合 `git bisect run` 的**二分 harness**。
9. 使用**差分循环**，比较旧版本与新版本、两套配置、两个 provider 或两份数据集。
10. 只有在别无选择时才使用 **human-in-the-loop 脚本**：将人工步骤脚本化并捕获结果，使循环保持结构化。

**循环建立后，进一步收紧它：**

- 让它更快：缓存 setup、缩小范围、跳过无关初始化。
- 让信号更明确：断言确切症状，而不是笼统的成功。
- 让它更具确定性：固定时间、设置随机种子、隔离文件系统、冻结网络。

对于非确定性 bug，眼下目标是提高复现率，而不是追求完美。将触发器运行 100 次、并行执行、增加压力、缩窄时序窗口，或注入 sleep。复现率 50% 的 flake 可以调试；复现率 1% 的通常不行。

**操作：** 使用 `terminal` 工具运行紧凑循环：

```bash
# Run a specific failing test
pytest tests/test_module.py::test_name -v

# Or run a scripted repro
python scripts/repro_bug.py

# Or run a high-repetition flaky repro
for i in {1..100}; do pytest tests/test_flake.py::test_name -q || break; done
```

### 3. 检查近期变更

- 哪些变更可能导致该问题？
- Git diff、近期 commit
- 新依赖、配置变更

**操作：**

```bash
# Recent commits
git log --oneline -10

# Uncommitted changes
git diff

# Changes in specific file
git log -p --follow src/problematic_file.py | head -100
```

### 4. 在多组件系统中收集证据

**当系统包含多个组件时（API → service → database、CI → build → deploy）：**

**提出修复方案之前，先加入诊断 instrumentation：**

对于每一个组件边界：
- 记录进入组件的数据
- 记录离开组件的数据
- 验证 environment/config 的传递
- 检查每一层的状态

运行一次，收集能表明故障发生在何处的证据。
然后分析证据，找出发生故障的组件。
再调查该特定组件。

### 5. 追踪数据流

**当错误位于调用栈深处时：**

- 错误值源自哪里？
- 哪个调用方把错误值传给了这个函数？
- 持续向上游追踪，直到找到源头
- 在源头修复，而不是在症状处修补

**操作：** 使用 `search_files` 追踪引用：

```python
# Find where the function is called
search_files("function_name(", path="src/", file_glob="*.py")

# Find where the variable is set
search_files("variable_name\\s*=", path="src/", file_glob="*.py")
```

### 阶段 1 完成检查清单

- [ ] 已完整阅读并理解错误消息
- [ ] 已有一条紧凑循环命令，并且至少运行过一次
- [ ] 循环能够变红：它断言的是用户的确切症状，而非邻近的其他故障
- [ ] 循环具有确定性；如果是 flaky bug，则复现率已足够高，可以调试
- [ ] 已识别并审查近期变更
- [ ] 已收集证据（日志、状态、数据流）
- [ ] 已将问题隔离到特定组件/代码
- [ ] 能够陈述并检验 root cause 假设

**停止：** 在理解问题为何发生之前，不要进入阶段 2。

## 阶段 2：模式分析

**先找到模式，再进行修复：**

### 0. 最小化复现

循环变红后，将复现缩减到仍能变红的最小场景。每次只删减输入、调用方、配置、数据或步骤中的**一项**，每次删减后都重新运行循环。只保留对故障不可或缺的部分。

当移除任一剩余元素都会使循环变绿时，即告完成。最小复现可以缩小假设空间，而且往往会成为最干净的回归测试。

### 1. 查找正常工作的示例

- 在同一代码库中找到相似且正常工作的代码
- 有哪些与故障代码相似的代码能够正常工作？

**操作：** 使用 `search_files` 查找可比较的模式：

```python
search_files("similar_pattern", path="src/", file_glob="*.py")
```

### 2. 与参考实现比较

- 如果要实现某种模式，请完整阅读参考实现
- 不要略读——每一行都要读
- 充分理解该模式后再应用

### 3. 找出差异

- 正常部分与故障部分有何不同？
- 列出每一处差异，无论多么细微
- 不要假设“这不可能有影响”

### 4. 理解依赖关系

- 它还需要哪些组件？
- 需要哪些设置、配置和环境？
- 它依赖哪些假设？

---

## 阶段 3：假设与检验

**采用科学方法：**

### 1. 形成有优先级、可证伪的假设

- 在检验任何单一假设之前，先提出 3–5 个合理假设。
- 按可能性以及证伪成本的高低对它们排序。
- 陈述每个假设所作的预测：“如果 X 是原因，那么改变或观察 Y 应该会使 Z 发生。”
- 如果某个假设无法给出可检验的预测，就舍弃它或使其更精确。

如果用户在线，检验前先展示排序后的列表。用户可能掌握领域知识，能立即改变排序。如果用户 AFK，则按自己的排序继续。

### 2. 以最小方式检验

- 用尽可能小的探针检验排名最高的假设。
- 每次只改变一个变量。
- 不要同时修复多个问题。
- 如果可用，优先通过 debugger/REPL 检查；一个 breakpoint 胜过十条日志。
- 如果添加日志，为每一条临时日志加上唯一前缀，例如 `[DEBUG-a4f2]`，以便一次搜索即可完成清理。

### 3. 继续之前先验证

- 奏效了吗？→ 进入阶段 4
- 没奏效？→ 形成新的假设
- 不要在现有尝试上继续叠加修复

### 4. 不知道时怎么办

- 明确说“我不理解 X”
- 不要假装知道
- 向用户求助
- 做更多调研

---

## 阶段 4：实施

**修复 root cause，而不是症状：**

### 1. 创建失败测试用例

- 使用尽可能简单的复现
- 尽可能编写自动化测试
- 修复前必须具备该测试
- 使用 `test-driven-development` 技能

### 2. 实施单一修复

- 解决已识别的 root cause
- 每次只做一项变更
- 不要顺手做其他“既然都到这里了”的改进
- 不要捆绑重构

### 3. 验证修复

```bash
# Run the specific regression test
pytest tests/test_module.py::test_regression -v

# Run full suite — no regressions
pytest tests/ -q
```

### 4. 如果修复无效——三次法则

- **停止。**
- 数一数：已经尝试过多少次修复？
- 如果 < 3：回到阶段 1，结合新信息重新分析
- **如果 ≥ 3：停止并质疑架构（见下方第 5 步）**
- 未经架构层面的讨论，不要尝试第 4 次修复

### 5. 如果 3 次以上修复均失败：质疑架构

**表明架构存在问题的模式：**
- 每次修复都会在不同位置暴露新的共享状态/耦合
- 修复需要“巨量重构”才能实施
- 每次修复都会在其他地方产生新症状

**停下来，质疑基本前提：**
- 这种模式从根本上是否合理？
- 我们是否“纯粹出于惯性而坚持”？
- 应该重构架构，还是继续修补症状？

**尝试更多修复之前，先与用户讨论。**

这不是假设失败——而是架构错误。

## 危险信号——停止并遵循流程

如果发现自己产生以下想法：
- “现在先快速修一下，以后再调查”
- “先改改 X，看看是否有效”
- “一次加上多项变更，然后运行测试”
- “跳过测试，我手动验证”
- “很可能是 X，让我先修它”
- “我还没完全理解，但这样也许能行”
- “模式要求 X，但我要用不同方式调整它”
- “主要问题如下：[未调查就列出修复方案]”
- 还没追踪数据流就提出解决方案
- **“再尝试一次修复”（此前已经尝试 2 次以上）**
- **每次修复都会在不同位置暴露一个新问题**

**以上任何一项都意味着：停止。回到阶段 1。**

**如果 3 次以上修复均失败：** 质疑架构（阶段 4 第 5 步）。

## 常见的自我合理化

| 借口 | 事实 |
|--------|---------|
| “问题很简单，不需要流程” | 简单问题同样有 root cause。对于简单 bug，这套流程也很快。 |
| “情况紧急，没时间走流程” | 系统化调试比反复猜测和试错更快。 |
| “先试一下这个，再去调查” | 第一次修复会定下后续模式。从一开始就按正确方式做。 |
| “先确认修复有效，之后再写测试” | 未经测试的修复无法可靠留存。测试先行才能证明修复。 |
| “一次做多项修复更省时间” | 无法隔离究竟哪一项有效，而且会引入新 bug。 |
| “参考实现太长，我直接调整这个模式” | 一知半解必然导致 bug。完整阅读参考实现。 |
| “我看出问题了，让我来修” | 看到症状 ≠ 理解 root cause。 |
| “再尝试一次修复”（已经失败 2 次以上） | 失败 3 次以上 = 架构问题。应质疑该模式，而不是再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|------------------|
| **1. Root Cause** | 阅读错误、复现、检查变更、收集证据、追踪数据流 | 理解问题是什么以及为何发生 |
| **2. 模式** | 查找正常示例、比较、识别差异 | 知道差异所在 |
| **3. 假设** | 形成理论、最小化检验、每次只改一个变量 | 假设得到确认，或形成新假设 |
| **4. 实施** | 创建回归测试、修复 root cause、验证 | bug 已解决，所有测试均通过 |

## Hermes Agent 集成

### 调查工具

在阶段 1 使用以下 Hermes 工具：

- **`search_files`**——查找错误字符串、追踪函数调用、定位模式
- **`read_file`**——读取带行号的源代码，进行精确分析
- **`terminal`**——运行测试、查看 git history、复现 bug
- **`web_search`/`web_extract`**——调研错误消息和库文档

### 与 delegate_task 配合使用

对于复杂的多组件调试，派发调查 subagent：

```python
delegate_task(
    goal="Investigate why [specific test/behavior] fails",
    context="""
    Follow systematic-debugging skill:
    1. Read the error message carefully
    2. Reproduce the issue
    3. Trace the data flow to find root cause
    4. Report findings — do NOT fix yet

    Error: [paste full error]
    File: [path to failing code]
    Test command: [exact command]
    """,
    toolsets=['terminal', 'file']
)
```

### 与 test-driven-development 配合使用

修复 bug 时：
1. 编写能够复现 bug 的测试（RED）
2. 通过系统化调试找到 root cause
3. 修复 root cause（GREEN）
4. 由该测试证明修复有效并防止回归

## 实际效果

根据调试会话统计：
- 系统化方法：15–30 分钟完成修复
- 随机尝试方法：反复折腾 2–3 小时
- 首次修复成功率：95%，而非 40%
- 引入新 bug：接近于零，而非经常发生

**不走捷径。不靠猜测。系统化方法永远胜出。**
