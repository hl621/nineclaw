# 为何使用台账编号 id（有据可查设计的研究依据）

本文是供修改引用说明或台账机制的人参考的设计笔记。SKILL.md 中的措辞并非随意制定。

## 结构上的关键技巧

当模型凭记忆重建 URL 时，就会产生虚构引用。如果模型唯一需要输出的内容，是检索时
提供给它的一个小整数，那么就没有任何内容需要重建——错误 id 可以被检测出来
（它不在台账中），错误 URL 则不可能出现（模型从不输入 URL；由 `render` 完成）。
这正是 Perplexity 产品所依赖的特性，也是 URL 必须由台账而非正文掌管的原因。

由此得出结论：**检索时登记，以机械方式渲染。** 任何允许模型在 Sources 区块中
自行输入 URL 的流程，都会主动放弃这项保证。

## 边写边引用，而不是事后补充

ALCE（arXiv:2305.14627）评估了 LLM 回答的归属标注，发现依据带编号的已检索片段，
在写作过程中同步生成引用，其归属准确性显著优于事后插入引用。事后归属会诱使模型
寻找一个看似匹配它已经写好句子的来源——这正是引用最终支撑了页面并未陈述内容的
原因。

因此：每写出一个有来源支撑的句子，就立即逐句添加内联引用。绝不要在段落或文档
末尾集中堆放引用。

## 逐字引文让论断有据可查

WebGPT（arXiv:2112.09332）会在浏览时收集逐字引文，并据此组织回答。本技能的实用
规则是：当论断包含数字、日期、名称或数量时，应从来源的原话中获取，而不要对已经
过转述的摘要再次转述。每多经过一次摘要，就多一次数字发生偏移的机会。

## 格式约定

以下约定源自 Perplexity 泄露的系统提示词（jujumilk3/leaked-system-prompts）——值得
照搬，因为用户已经习惯阅读这种格式：

- 标记紧跟在句末标点后，不留空格：`water.[1]`
- 每个 id 单独使用一对方括号：`[1][2]`，而不是 `[1, 2]`
- 每句最多 3 个 id——超过这个数量后，引用便无法说明究竟哪个来源支撑该论断
- 绝不引用未实际查阅的来源
- 不应添加引用的查询类别（翻译、创意写作、闲聊）通过指令豁免，而不是依赖单独的
  分类器

Perplexity 禁止在回答中出现原始 URL，因为其 UI 会渲染来源卡片。Hermes 在聊天或
书面文件中没有这样的 UI 层，因此本技能会改为明确渲染 id → URL 列表。

## 代码树中的相关实现

`tools/web_tools.py` 在 PR #44833 中加入了这一思路的进程内版本（一个
`url -> [n]` 注册表，以及附加在工具结果中的引用指南）。该路径落地后，会自动让
临时 Web 回答具备来源依据。本技能则是其中可移植的另一半：它适用于任何检索来源
（浏览器、curl、CLI、本地 PDF），并将台账持久保存到磁盘，从而让跨轮次、多文件、
多子代理工作保持 id 稳定。二者可以共存——对于任何写入文件的内容，台账都是唯一
事实来源。
