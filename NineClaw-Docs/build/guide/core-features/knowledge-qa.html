知识问答

知识问答的目标不是简单地“把问题丢给知识库，再把召回片段拼给大模型”。在 NineClaw 中，QY-RAG 主要承担文档解析、切片、召回和重排等检索能力；问答链路本身由 NineClaw-Manager 和 Runtime/Agent 侧组织，围绕“如何问得更准、如何判断证据是否足够、如何避免无依据回答”做优化。

这一设计参考了 Google Research 在 Gemini Enterprise Agent Platform Agentic RAG 中提出的方向：标准 RAG 对复杂、多跳、多来源问题容易停在第一次检索结果上，而 Agentic RAG 会进行规划、查询改写、检索分发、充分上下文判断和必要的迭代检索。

设计边界​

NineClaw 并不把 QY-RAG 当成完整问答黑盒使用。更准确的分工是：

模块职责
QY-RAG负责知识库、文档、切片、召回、相似度排序和重排能力
NineClaw-Manager负责知识库 API 包装、检索参数组织、引用片段过滤、问答模型选择和 SSE 输出
Runtime / Agent负责在复杂任务中决定是否使用 RAG、如何改写查询、是否需要再次检索
LLM基于已召回证据生成回答，并按引用编号标注来源

也就是说，QY-RAG 提供“找证据”的能力；NineClaw 负责“怎样找、找几次、够不够、怎么回答”。

为什么不只做一次召回​

传统 RAG 的常见流程是：

用户问题 -> 向量召回 -> 取 TopK 片段 -> LLM 生成答案

这个流程适合简单问题，但遇到以下情况容易失败：

场景问题
多跳问题第一次召回只找到中间线索，还需要继续查第二层信息
术语不一致用户问题和文档中的表达不同，直接召回命中率低
多知识库问题需要先判断应该查哪个知识库或哪类文档
证据不足TopK 里有相似内容，但不足以支撑完整答案
片段过散有相关片段，但需要重新组织、扩展上下文或补充检索

Google 的 Agentic RAG 研究强调的关键点是：系统应该能识别“当前上下文是否足够”，如果不够，就带着缺口反馈继续检索，而不是直接猜测或过早回答。

NineClaw 的知识问答也沿着这个方向设计：QY-RAG 负责高质量召回和重排，NineClaw 在外层增加面向问答的查询组织、引用筛选和回答约束。

当前实现链路​

Manager 侧主要有两类知识库接口，以及详情页 Studio 问答入口：

接口作用
POST /v1/knowledge/retrievalRAGFlow 兼容的检索测试接口，返回 chunks、doc_aggs、total
POST /v1/knowledge/qa全局 / 多库知识问答（AgenticRAG），SSE 返回 references 和 content
POST /v1/knowledge/{kb_id}/studio/chat/qa单库详情「知识问答」（同一 AgenticRAG Agent，Studio 事件格式）

全局检索与单库详情共用同一套 Agno Knowledge Q&A Agent（create_knowledge_qa_agent + KnowledgeRAGToolkit）。差别只在检索范围（dataset_ids 长度）和 SSE 事件形状（全局页用 legacy references/content，详情页可展示工具步骤）。

问答链路大致如下：

  1. WebUI 提交用户问题、知识库范围（一个或多个）和可选模型参数。
  2. Manager 校验知识库是否存在，并解析问答模型。
  3. AgenticRAG Agent 按需调用工具，例如：
    • rag_retrieve：在选定知识库内召回并组织 references
    • rag_check_sufficient_context：判断证据是否足够
    • rag_expand_context / rag_grep_document：扩展或筛查文档上下文
  4. 工具内部通过 QY-RAG / 检索服务做向量召回与重排；Manager 过滤不可用片段。
  5. Agent 基于最终证据生成带引用编号的回答（常见 [1]；亦可能出现 【1】），并做越界引用消毒。
  6. WebUI 通过 SSE 展示：全局检索页在 Agent 运行中可尽早收到 references，但界面上须等回答正文流式全部结束后，才在下方逐条展示资料来源；详情页可流式展示工具与推理步骤。

这个流程中，QY-RAG 只负责检索质量；查询改写、多轮检索、充分上下文判断、引用约束由 NineClaw AgenticRAG Agent 控制。用户操作说明见手册：RAG — 全局检索。

Agentic RAG 在 NineClaw 中的落点​

Google 文章中提到的 Agentic RAG 不是单个检索器，而是一组协作角色：Orchestrator 判断任务复杂度，Planner 规划信息路径，Query Rewriter 改写查询，Search Fanout 分发检索，Sufficient Context Agent 判断证据是否足够，最后再合成答案。

NineClaw 已将核心思路落到同一 Agent 上：

Agentic RAG 思路NineClaw 中的落点
OrchestrationAgno Agent 决定是否检索、是否补搜、何时作答
Planning复杂问题可拆成多个检索查询（rag_retrieve 内查询分解）
Query RewritingAgent 换关键词重试检索
Search Fanoutdataset_ids 多库召回；全局检索与单库共用同一工具
Sufficient Contextrag_check_sufficient_context
Iteration证据不足时补搜、扩展上下文或文档级筛查
Synthesis基于最终 references 生成带引用回答

重点不是替代 QY-RAG，而是在召回与重排之上增加一层可维护的查询智能，且全产品只维护这一套 Agent。

充分上下文判断​

知识问答最容易出问题的地方，是“看起来召回到了相关片段，但其实证据不够”。因此，充分上下文判断是优化重点。

判断时可以关注：

检查项说明
问题要点是否全部覆盖如果问题问三个条件，references 只覆盖两个，就不能直接回答完整结论
关键事实是否有来源每个关键事实都应能对应到一个召回片段
片段是否只是相似相似度高不等于能回答，需要看文本是否包含答案所需信息
是否需要上下文扩展命中片段可能只包含局部内容，需要查看前后片段或原文
是否应该停止多次检索仍无证据时，应明确说明知识库未找到，而不是继续猜

这也是 Agentic RAG 的核心价值：它不是无限检索，而是让系统知道“缺什么、还要查什么、什么时候可以停”。

与 QY-RAG 的关系​

QY-RAG 在这里承担的是底层检索引擎角色。NineClaw 侧不重复实现向量召回、文档切片和重排，而是使用 QY-RAG 已有能力：

QY-RAG 能力NineClaw 使用方式
文档解析将上传文档解析成可检索切片
切片管理管理文档 chunk、启用/停用和状态
相似度召回根据问题从指定 dataset/document 中召回候选片段
重排优先返回更可能支撑答案的片段
RAGFlow 兼容接口Manager 通过兼容请求体组织检索参数

NineClaw 的重点是把这些检索能力接入到统一 WebUI、模型管理、Runtime Agent 和 SSE 问答体验中。

回答约束​

知识问答的回答应遵守以下规则：

  1. 优先依据 references 中的事实回答。
  2. 关键结论必须带引用编号，例如 [1]、[2]（前端亦识别全角 ［n］ 与中文 【n】）。
  3. references 不足时，应说明“知识库中未找到足够信息”。
  4. 不把模型常识伪装成知识库证据。
  5. 多轮对话时，可以压缩历史，但不能让历史覆盖当前召回证据。

这些规则能让回答更可审计：用户不仅看到答案，也能看到答案依赖哪些文档片段。

后续演进​

在已统一的 AgenticRAG Agent 上，可继续增强：

方向说明
全局页工具时间线将全局检索接到 Studio 事件格式，展示检索/补搜步骤
多知识库路由根据问题类型自动选择知识库，减少手动勾选
缺口反馈可视化把「缺什么、还要查什么」展示给用户
证据评分将相似度、重排分、覆盖度、来源质量综合成回答可信度
回答审查在最终输出前检查是否每个关键事实都有引用

这些能力都可以在同一 Agent 上扩展，而不改变 QY-RAG 作为召回与重排引擎的定位，也不再维护第二条问答管道。
