批量部署

这里的“批量部署”不是指 NineClaw-Deploy 项目，也不是把整套系统安装到机器上。它指的是用户在 WebUI 中选择平台资源后，把这些资源应用到一个或多个已经运行的 NineClaw-Runtime 实例中。

批量部署覆盖五类资源：Models、Skill、MCP、RAG、WebSearch。它们的共同点是都不需要重新构建 Runtime 镜像，而是由 Manager 把平台侧保存的配置、环境变量或文件下发到多个目标 Runtime，再让 Runtime 重新加载；差异在于，Models、Skill、MCP 更偏“把能力装进 Runtime”，RAG、WebSearch 更偏“把插件配置进 Runtime，让 Runtime 在执行任务时反向调用外部服务”。

总体思路​

批量部署的核心链路可以分成三层：

层级负责内容
WebUI提供选择能力、选择 Runtime 实例、发起部署、查看部署结果的界面
Manager保存平台侧能力配置，校验租户和实例状态，编排对 Runtime 的配置写入、环境变量写入、文件拷贝和重启
Runtime接收配置和文件，在运行时加载模型、MCP、Skill、RAG 插件、WebSearch 插件，并在对话或任务执行中使用这些能力

Manager 面向 Runtime 的访问链路是：

nineclaw-manager
  -> http://traefik:80/traefik/nineclaw/{instance_id}/dashboard/api/...
  -> nineclaw-{instance_id}:8644/api/...

也就是说，Manager 不直接依赖 Runtime 容器 IP，而是通过 Traefik 内部入口访问每个 Runtime 的 Dashboard API。常用落点包括：

Runtime API用途
PUT /api/config写入 Runtime 配置，例如模型供应商、MCP Server、Skill 外部目录等
PUT /api/env写入 Runtime 环境变量，例如插件服务地址、API Key、搜索源范围等
POST /api/gateway/restart让 Gateway 重新读取模型、MCP、插件等配置
POST /api/model/set设置辅助任务模型，例如视觉、网页抽取、压缩等任务模型

因此，批量部署本质上是“运行时配置编排”，不是“重新安装系统”。它解决的是：平台里已经维护好的资源，如何一次性应用到多个 Runtime 实例中。

五类资源的批量部署差异​

能力Manager 保存什么Runtime 接收什么生效方式
ModelsProvider、Base URL、API Key、模型列表、默认模型、辅助模型分配custom_providers、model、辅助任务模型设置写入配置后由 Gateway/模型管理逻辑读取
Skill技能目录、SKILL.md、脚本、资源文件外部技能目录和 skills.external_dirs 配置拷贝文件后由 Runtime 从外部目录发现并加载
MCPMCP Server 名称、类型、命令、参数、URL、Headermcp_servers 配置块写入配置后重启 Gateway 重新连接
RAG知识库、数据集、RAGFlow/QY-RAG 连接信息、授权范围QYRAG_* 环境变量和 QYRAG 插件工具Runtime 在需要知识库证据时调用插件，插件再访问 QY-RAG/RAGFlow
WebSearchWebSearch 服务、搜索源、抽取能力、可选搜索源范围NINECLAW_WEBSEARCH_* 环境变量和 WebSearch 插件工具Runtime 在需要公网检索时调用插件，插件再访问 NineClaw-WebSearch

前三类能力是直接增强 Runtime 的本地配置；后两类能力虽然部署方式也依赖 Runtime 配置和环境变量，但运行时方向是反过来的：任务由 Runtime 内部的 Agent 发起，插件再调用 RAG 或 WebSearch 服务，把检索结果返回给 Agent 上下文。

Models 部署​

Models 部署对应 WebUI 中的模型供应商和模型选择能力。用户先在 Manager 中维护 Provider，例如 OpenAI-compatible endpoint、API Key、可用模型列表等；部署时再选择要应用到哪些 Runtime 实例。

部署时，Manager 调用 /v1/providers/deploy，读取目标 Runtime 当前配置，合并 custom_providers 和默认 model，再通过 Runtime Dashboard 的 PUT /api/config 保存。如果用户同时配置了辅助任务模型，Manager 会继续调用 Runtime Dashboard 的 /api/model/set，把模型绑定到具体任务上。

Manager 中的数据Runtime 中的落点说明
Provider 名称custom_providers[].nameRuntime 内部识别供应商
Base URLcustom_providers[].base_urlOpenAI-compatible endpoint
API Keycustom_providers[].api_key 或环境变量Runtime 调用模型时使用
模型列表custom_providers[].modelsRuntime 可选模型
主模型model默认对话模型
辅助模型/api/model/set视觉、网页抽取、压缩等任务模型

典型流程：

  1. WebUI 调用 /v1/providers/deploy。
  2. Manager 校验 Provider 和目标 Runtime 实例是否属于当前租户。
  3. Manager 确认目标 Runtime 处于运行状态。
  4. Manager 读取 Runtime 当前配置。
  5. Manager 合并 Provider、主模型和辅助模型配置。
  6. Manager 写入 Runtime 配置，并通过 SSE 返回每个实例的部署结果。

Skill 部署​

Skill 和 Models、MCP 不完全一样。Models 和 MCP 主要是配置型能力；Skill 是文件型能力，核心内容是一个技能目录，例如 SKILL.md、脚本、资源文件等。

Manager 侧使用 skills_storage 保存技能包。部署到 Runtime 时，Manager 会确保 Runtime 配置中的 skills.external_dirs 包含 /opt/nineclaw/external_skill，然后通过 Docker API 把选中的 Skill 目录拷贝进目标 Runtime 容器。

操作说明
更新 Runtime 配置确保 skills.external_dirs 包含 /opt/nineclaw/external_skill
准备容器目录在目标 Runtime 容器中创建 /opt/nineclaw/external_skill
拷贝技能文件将 Manager skills_storage 中的技能目录打包并写入 Runtime 容器

典型流程：

  1. 用户上传或导入 Skill，Manager 将技能目录保存到 skills_storage。
  2. WebUI 调用 /v1/skills/deploy，指定 Skill 和目标 Runtime 实例。
  3. Manager 校验 Skill 是否存在，校验目标实例是否运行中。
  4. Manager 读取 Runtime 当前配置，补齐外部技能目录。
  5. Manager 通过 Docker API 在目标容器中创建目录并拷贝 Skill 文件。
  6. Runtime 后续从外部目录发现并加载技能。

MCP 部署​

MCP 部署对应把一个或多个 MCP Server 写入 Runtime 的 mcp_servers 配置块。MCP Server 在 Manager 中按租户保存，支持 stdio 和 url 两类形态。

类型Runtime 配置内容
stdiocommand、args、env，由 Runtime 启动本地 MCP 进程
urlurl、headers，由 Runtime 调用远端 MCP 服务

部署时，Manager 调用 /v1/mcps/deploy，读取目标 Runtime 当前配置，把选中的 MCP Server 合并到 mcp_servers 中。同名 MCP 会被新的配置覆盖，其他 MCP 保留。保存配置后，Manager 调用 /api/gateway/restart，让 Gateway 重新读取 MCP 配置并建立新的连接。

典型流程：

  1. WebUI 调用 /v1/mcps/deploy。
  2. Manager 校验 MCP Server 和目标 Runtime 实例。
  3. Manager 读取 Runtime 当前配置。
  4. Manager 合并 mcp_servers 配置块。
  5. Manager 写入 Runtime 配置。
  6. Manager 重启 Runtime Gateway，等待动作完成。
  7. Manager 通过 SSE 返回每个实例的部署结果。

RAG 部署​

RAG 与 Models、Skill、MCP 的思路相似：也要把配置部署到 Runtime，也依赖 Runtime 的环境变量和重新加载。但 RAG 的使用方向不同。RAG 的知识库管理发生在 WebUI 和 Manager 侧，真正回答问题时，Runtime 内部的 Agent 通过 QYRAG 插件反向调用 QY-RAG/RAGFlow 检索接口。

Manager 侧有知识库 API 和 RAGFlow 适配层：WebUI 面向 Manager 的 /v1/knowledge/* 创建知识库、上传文件、解析文档、查看切片和做检索测试；Manager 再根据配置选择本地知识库后端或 RAGFlow/QY-RAG 后端。代码中 RagflowKnowledgeService 把 NineClaw 的知识库操作适配成 RAGFlow 的 dataset/document 操作，RagflowClient 负责访问 RAGFlow /api/v1。

Runtime 侧通过 NineClaw-QYRAG 插件使用这些能力。插件声明并注册了以下工具：

工具作用
QYRAG_retrieve从授权知识库中召回切片
QYRAG_expand_context围绕命中的切片扩展上下文
QYRAG_save_document将文档材料保存到 Runtime 工作区
QYRAG_health_check检查 QY-RAG/RAGFlow 连通性和授权

RAG 部署到 Runtime 时，重点不是把知识库文件复制进 Runtime，而是把插件访问 QY-RAG/RAGFlow 所需的环境变量写入 Runtime：

环境变量说明
QYRAG_BASE_URLQY-RAG/RAGFlow 服务地址
QYRAG_API_KEY访问 QY-RAG/RAGFlow 的 API Key
QYRAG_DATASETSRuntime 可访问的数据集范围：JSON 对象，键为知识库显示名称、值为 dataset id。目标为可读中文，例如 {"策略分析": "afe3…"}。因 Hermes PUT /api/env 会剥离非 ASCII，Manager 部署后会再以容器 UTF-8 回写该行
QYRAG_OUTPUT_DIRQYRAG_save_document 保存材料的默认目录
QYRAG_MAX_RETRIES_HINT检索弱召回时的建议重试次数

部署后可在实例终端执行 cat /opt/data/.env 核对 QYRAG_DATASETS。操作步骤与截图见用户手册 RAG（知识库）— 部署到 NineClaw 实例。

部署后的调用方向是：

  1. 用户在 WebUI 中维护知识库或选择可用知识库范围。
  2. Manager 将 QY-RAG/RAGFlow 地址、API Key、数据集授权范围写入目标 Runtime 环境变量。
  3. Runtime 重新加载后发现 NineClaw-QYRAG 插件工具。
  4. 对话过程中，如果 Agent 判断需要内部文档证据，会调用 QYRAG_retrieve。
  5. 插件读取 Runtime 环境变量，访问 QYRAG_BASE_URL/api/v1/retrieval。
  6. 检索结果以结构化文本返回给 Agent，Agent 再结合模型生成回答。

这就是 RAG 的“反向运用”：知识库由平台侧管理，但不是 WebUI 每次替 Runtime 取好答案；而是 Runtime 在任务执行过程中主动调用插件检索知识库。

WebSearch 部署​

WebSearch 的部署方式和 RAG 很接近，也属于插件反向调用。NineClaw-WebSearch 是独立服务，负责搜索源管理、搜索聚合、网页正文抽取和列表链接抽取；WebUI 可以通过 Traefik 的 /ws-api 使用它，Runtime 也可以通过 NineClaw-WebSearch 插件在执行任务时主动调用它。

系统侧路由关系是：

外部路径服务内路径服务
/ws-api/search/v1/searchnineclaw-websearch:8000
/ws-api/extract_detail/v1/extract_detailnineclaw-websearch:8000
/ws-api/extract_listlink/v1/extract_listlinknineclaw-websearch:8000
/ws-api/sources/v1/sourcesnineclaw-websearch:8000

Runtime 侧的 NineClaw-WebSearch 插件注册了一个 WebSearch Provider，也注册了直接可调用的工具：

工具或 Provider作用
nineclaw WebSearch Provider接入 Runtime/Hermes 的通用 web search / web extract 调度
nineclaw_search调用 NineClaw-WebSearch /v1/search 获取搜索结果
nineclaw_extract调用 /v1/extract_detail 抽取网页正文
nineclaw_extract_listlink调用 /v1/extract_listlink 从列表页发现链接

WebSearch 部署到 Runtime 时，重点是写入插件服务地址和搜索范围：

环境变量说明
NINECLAW_WEBSEARCH_BASE_URLNineClaw-WebSearch 服务地址，可指向 http://nineclaw-websearch:8000 或 Traefik /ws-api
NINECLAW_WEBSEARCH_INCLUDE_SOURCES允许使用的搜索源列表
NINECLAW_WEBSEARCH_EXCLUDE_SOURCES排除的搜索源列表
NINECLAW_WEBSEARCH_TAGS按标签筛选搜索源

部署后的调用方向是：

  1. WebUI/Manager 维护 WebSearch 服务、搜索源和可用范围。
  2. Manager 将 WebSearch 访问地址和搜索源限制写入目标 Runtime 环境变量。
  3. Runtime 重新加载后注册 NineClaw-WebSearch 插件。
  4. 对话过程中，如果 Agent 需要最新公开信息，会调用 nineclaw_search 或通用 web search provider。
  5. 插件访问 NineClaw-WebSearch 的 /v1/search、/v1/extract_detail、/v1/extract_listlink。
  6. 搜索和抽取结果返回给 Agent，Agent 再判断证据质量并生成回答。

WebSearch 与 RAG 的边界也体现在插件描述里：RAG 优先用于用户上传的内部资料、政策、合同、手册、报告等文档证据；WebSearch 优先用于新闻、最新事实、公开网页发现和知识库之外的信息补充。两者可以组合使用，先用 WebSearch 获取当前公开背景，再用 RAG 查内部文档证据，或者先用 RAG 命中文档后再用 WebSearch 做公开信息校验。

统一重启和重载​

批量部署最终都要解决一个问题：配置写进 Runtime 之后，运行中的服务什么时候读取新配置。

能力常见刷新方式
Models写入配置后由模型管理逻辑或 Gateway 读取
Skill拷贝文件后由 Runtime 从外部目录发现，必要时重启或重载
MCP写入配置后重启 Gateway
RAG写入环境变量后重启或重载 Runtime，使插件读取新的 QYRAG_*
WebSearch写入环境变量后重启或重载 Runtime，使插件读取新的 NINECLAW_WEBSEARCH_*

这也是五类部署能力的共性：不是重新打包镜像，而是利用 Runtime Dashboard API、容器级文件操作、环境变量修改和 Gateway/Runtime 重启，让已经运行的 Runtime 获得新的能力。

和 NineClaw-Deploy 的区别​

名称作用
NineClaw-Deploy交付整套系统，负责镜像、Compose、离线包、安装脚本
批量部署把 Models、Skill、MCP、RAG、WebSearch 等资源应用到一个或多个已运行的 Runtime 实例

前者解决“系统怎么安装起来”，后者解决“某个资源怎么批量应用到多个 Runtime 实例，并在 Runtime 任务执行中被使用”。
