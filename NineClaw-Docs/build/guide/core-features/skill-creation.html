技能创建

技能创建解决的是“如何把一个可复用的工作方法沉淀成 Runtime 可加载的能力”。它不是简单保存一段 Prompt，也不是只在页面里填一个名称和描述；更完整的思路是：用户提出目标，系统用专门面向 Skill 编写的智能体把目标整理成规范化的 SKILL.md、参考资料、脚本和测试说明，再由 Manager 做文件级校验、保存和部署。

开放标准与目录结构​

Skill 不是 NineClaw 自己发明的一种私有格式，而是来自 Agent Skills Open Standard 这类开放规范的能力包形态。Agent Skills Open Standard 由 Anthropic 提出并开源，用于定义 AI 智能体可以加载和使用的能力包；agentskills.io 是该标准的官方独立主页，可以查看完整 Specification、SKILL.md 编写要求、元数据字段和生态支持情况。

它的价值在于跨产品复用：同一个 Skill 目录可以被支持该规范的 Agent 客户端识别和加载。公开规范中对 Skill 的基本理解很简单：一个 Skill 就是一个文件夹，至少包含一个 SKILL.md 文件，也可以附带脚本、参考资料、模板和其他资源。更多规范说明可参考 Agent Skills Specification。

一个典型 Skill 目录可以这样理解：

my-skill/
├── SKILL.md          # 必需：元数据 + 给 Agent 的使用说明
├── scripts/          # 可选：可执行脚本，例如 Python、Bash、JavaScript
├── references/       # 可选：领域资料、规则、示例、检查清单
├── assets/           # 可选：模板、样例、图片、数据文件等静态资源
├── README.md         # 可选：给维护人员看的说明
└── ...               # 可选：其他和该 Skill 相关的文件

各部分的作用如下：

内容作用
SKILL.mdSkill 的核心文件，包含 YAML frontmatter 和正文说明
references/领域资料、规则、示例、检查清单等参考内容
scripts/可复用脚本，适合处理稳定、机械、可验证的步骤
assets/模板、样例、静态资源等辅助材料
README.md面向维护人员的说明，可选

其中 SKILL.md 是最低要求。根据 Agent Skills 规范，SKILL.md 至少需要包含 name 和 description，正文部分则用于告诉 Agent 什么时候使用这个 Skill、按什么步骤执行、遇到边界情况如何处理。

NineClaw 在这个开放结构之上做管理和部署：Manager 会识别包含 SKILL.md 的目录，读取标准元数据和 NineClaw 需要的扩展信息，将整个目录作为一个可管理、可导入、可编辑、可批量部署的能力资产。

为什么需要专业智能体​

手工写 Skill 容易出现几个问题：

问题影响
只写成普通 PromptAgent 不知道何时使用、如何分阶段执行、如何验收
缺少边界条件容易把 Skill 写得过宽，和普通对话能力重叠
缺少文件结构复杂技能里的参考资料、脚本、模板无法沉淀
缺少验证标准生成后无法判断 Skill 是否真的可用

因此，技能创建时引入“专业智能体”更合理。这个智能体的职责不是直接完成用户业务任务，而是充当 Skill 工程师：理解用户想沉淀的能力，拆解适用场景、输入输出、执行步骤、依赖文件和验收标准，然后生成或修改 Skill 文件。

这种设计把“做一次任务”和“沉淀一个可复用能力”分开。普通 Agent 负责完成当次任务；Skill 创建智能体负责把稳定的方法论写成未来可重复加载的能力包。

总体流程​

技能创建可以理解为四个阶段：

阶段说明
需求理解用户描述希望沉淀的能力，例如“帮我创建一个合同审查 Skill”
能力建模专业智能体判断适用场景、触发条件、输入输出、执行步骤和验收标准
文件生成生成 SKILL.md，必要时补充 references/、scripts/、assets/
校验入库Manager 校验 Skill 目录结构和 frontmatter，保存到 SKILLS_STORAGE_PATH

完成入库后，Skill 还只是平台侧的能力资产。要让一个或多个 Runtime 实例真正使用它，还需要走“批量部署”：Manager 将 Skill 目录拷贝到目标 Runtime 容器，并确保 Runtime 配置中的 skills.external_dirs 包含外部 Skill 目录。

专业智能体做什么​

专业智能体关注的是 Skill 的工程质量，而不是只生成一段自然语言描述。它通常会处理以下内容：

工作说明
明确适用范围说明什么时候应该使用这个 Skill，什么时候不应该使用
组织执行步骤把任务拆成可执行、可检查的阶段，而不是一整段笼统建议
设计输入输出明确用户需要提供什么、Skill 产出什么结果
沉淀参考资料把规则、术语、样例、检查清单放入 references/
识别脚本机会将稳定的解析、转换、校验动作沉淀为 scripts/
写验收标准让后续测试和人工 review 有判断依据
控制边界避免 Skill 过度泛化，导致它和普通对话能力混在一起

从大面上看，它相当于把“Prompt 编写”升级成“能力包设计”。结果不是一段孤立文本，而是一个 Runtime 可以加载、维护人员可以审阅、部署流程可以分发的目录。

和 Manager 的关系​

Manager 不负责理解业务需求本身，它负责 Skill 资产的管理和落盘。专业智能体生成或修改文件后，Manager 侧主要做这些事情：

Manager 能力作用
识别 Skill扫描 SKILLS_STORAGE_PATH 下包含 SKILL.md 的目录
解析元数据读取 SKILL.md frontmatter，形成列表页和详情页展示数据
校验结构校验 frontmatter、slug、路径安全、zip 包结构等
保存文件将 Skill 目录作为文件系统资产保存
导入导出支持 zip 上传、预览、SSE 流式导入和下载
部署分发将 Skill 拷贝到 Runtime 容器并更新外部目录配置

也就是说，专业智能体负责“把需求变成合格 Skill”，Manager 负责“把合格 Skill 管起来、校验好、分发出去”。

和 Runtime 的关系​

Runtime 不关心 Skill 是人工写的还是智能体生成的。只要目录结构符合约定，并且 Runtime 能在外部 Skill 目录中发现它，就可以在后续任务中加载使用。

Runtime 侧真正关心的是：

Runtime 关注点说明
Skill 是否可发现目录是否位于 skills.external_dirs 指定路径下
SKILL.md 是否清晰是否说明触发条件、执行步骤、限制和验收方式
附属文件是否可用references/、scripts/、assets/ 是否能被 Agent 按说明调用
运行时成本是否合理是否避免把过大的资料、过多步骤无条件塞进上下文

因此，技能创建的质量会直接影响 Runtime 的实际使用效果。写得好的 Skill 会让 Agent 更稳定地完成特定类型任务；写得过宽、过空或缺少约束的 Skill，则容易退化成普通提示词。

关键原则​

技能创建时建议遵循以下原则：

  1. 先限定场景，再写执行步骤。不要先追求“万能”，应先说清楚它适合什么问题。
  2. 能沉淀为文件的内容就沉淀为文件。长规则、示例和检查清单不要都塞进 SKILL.md 主体。
  3. 能用脚本稳定完成的步骤就用脚本。解析、格式转换、批量检查这类动作适合放入 scripts/。
  4. 给出明确验收标准。Skill 的输出应该能被人工或自动流程检查。
  5. 创建后要测试。用典型输入跑一遍，看 Agent 是否能正确理解触发条件和执行流程。

和普通 Skill 管理的区别​

能力重点
技能创建用专业智能体把用户需求工程化为 Skill 目录和文件
上传 Skill导入已有 Skill 包，重点是识别、预览、冲突处理和安装
编辑 Skill在 Studio 中修改 SKILL.md 或附属文件，持续迭代能力
部署 Skill将选中的 Skill 分发到目标 Runtime 实例，使其在任务执行中可用

因此，“技能创建”是能力生命周期的起点；“批量部署”是把这个能力应用到 Runtime 的最后一步。
