信源管理

Hermes 在复杂任务中的表现，很大一部分来自 web_search 这类工具能力：模型不只依赖自身参数中的静态知识，而是可以在任务过程中主动搜索、抽取页面、补充证据，再基于最新或最贴近场景的信息作答。

在离线或私有化部署环境中，系统不能默认访问公网搜索引擎，但“搜索外部信息”的能力仍然重要。NineClaw 的信源管理就是为这个场景设计的：用户可以把内网搜索、文档门户、知识平台、业务系统查询接口、离线镜像站点等信息源快速接入 WebSearch，让 Runtime 中的 Agent 继续通过统一的 WebSearch 工具发现和汇聚信息。

解决什么问题​

离线环境下的信息通常分散在多个系统里：

信息来源常见形态接入后的价值
内网搜索企业搜索接口、门户搜索页让 Agent 能像使用搜索引擎一样检索内部资料
文档平台Wiki、知识门户、制度库、手册站点补充 RAG 知识库之外的动态或半结构化内容
业务系统工单、项目、资产、流程系统接口让回答能引用业务现场数据
离线镜像离线网页、法规库、公开资料镜像在无公网环境下保留广域检索能力
自定义服务用户已有 API、数据库检索网关把行业系统纳入统一搜索工具链

信源管理的重点不是把所有数据提前灌入知识库，而是把“可搜索、可抽取、可汇聚”的入口管理起来。这样，当用户问题需要临时发现信息时，Agent 可以按需搜索，再对关键结果做详情抽取。

整体分工​

信源能力分成管理面和执行面两部分：

模块职责
NineClaw-WebUI提供信源配置、请求调试、提取器编辑、验证结果查看等界面
NineClaw-Manager保存租户级信源配置，提供 CRUD、代理请求、提取器运行、AI 生成提取器、专业智能体修复提取器等接口
NineClaw-WebSearch执行真正的搜索、并发请求、页面抽取、列表链接抽取、去重、融合排序
NineClaw-Runtime通过 NineClaw-WebSearch 插件把搜索能力注册为 Hermes 的工具和 web_search provider
Traefik把 /ws-api 路由到 WebSearch 服务，供 WebUI、Manager 或 Runtime 在容器网络中访问

这个边界很关键：Manager 负责“谁能配置什么信源、信源怎么调试、提取器是否可用”；WebSearch 负责“收到查询后如何高并发访问多个信源、如何解析结果、如何合并排序”。

Manager 侧能力​

Manager 中的信源模型是租户化的配置对象。web_sources 表保存信源名称、类型、入口地址、启用状态、请求配置、提取器代码、URL 基准地址和验证状态。

核心字段可以理解为：

字段说明
tenant_id信源归属租户，避免不同用户或组织之间配置混用
name / description / type信源的可读名称、说明和分类
url / url_base搜索入口或结果链接补全基准地址
enabled是否参与搜索
request_config请求方法、参数、请求头、请求体、代理等配置
extractor_code将 HTML 响应解析为 url、title、desc 的 Python 提取器
is_verified是否已通过调试验证

围绕这些配置，Manager 提供几类能力：

能力作用
信源 CRUD创建、更新、删除、查询当前租户的信源
代理请求帮助前端调试目标地址、参数、请求头和代理配置
代码格式化对提取器代码进行格式化，降低维护成本
提取器运行在沙箱中执行用户提供的 extract(html)，验证输出结构
AI 生成提取器根据 HTML 和用户说明生成 Python 提取代码
Agent 编辑提取器让专业代码智能体根据 HTML 样例和修改要求修复 extract.py
聚合搜索入口面向 AI 调用，将查询分发到已启用信源并返回各信源结果

提取器运行时有明确的安全边界：代码在沙箱中执行，限制 CPU 和内存，并校验每一条结果必须包含 url、title，可选 desc。这让用户可以灵活适配各种内网页面，同时避免把不可靠代码直接放进 Manager 主进程执行。

WebSearch 侧能力​

NineClaw-WebSearch 是独立服务，核心目标是把不同来源统一成搜索和抽取 API。服务对外提供 /v1/search、/v1/extract_detail、/v1/extract_listlink 等接口。

搜索链路大致如下：

  1. 读取已配置的信源。
  2. 按 enabled、标签、include/exclude 列表过滤可用信源。
  3. 对多个信源并发发起请求。
  4. 将查询词填入信源请求模板中的 URL、参数、Header 或 Body。
  5. 对每个信源返回的 HTML 执行对应 extract()。
  6. 将相对链接按 url_base 补全。
  7. 对同标题或相似标题结果去重。
  8. 按信源权重和排序位置进行融合打分。
  9. 返回统一结构的搜索结果和每个信源的执行统计。

详情抽取和列表链接抽取也是独立能力。extract_detail 用于对搜索命中的具体 URL 抽取正文；extract_listlink 用于从栏目页、列表页、专题页中发现更多链接。两者都通过并发控制和 URL 数量限制避免单次任务压垮服务。

为什么 WebSearch 独立成项目​

WebSearch 从 Manager 中拆出来，主要是出于并发、稳定性和组件共性的考虑。

原因说明
高并发 I/O搜索任务会同时访问多个信源，并且涉及网络超时、代理、重试、HTML 解析等 I/O 密集操作
故障隔离某个信源慢、不可达或解析失败，不应该拖垮 Manager 的核心管理接口
独立扩缩容企业信源越多，搜索压力越大，WebSearch 可以单独扩容
组件复用WebUI 调试、Manager 聚合、Runtime 工具调用、Hermes web_search provider 都可以复用同一个服务
统一协议不同信源最终被归一成搜索、正文抽取、列表链接抽取三类稳定接口

因此，Manager 更像控制平面，负责信源生命周期和租户配置；WebSearch 更像执行平面，负责把查询真正跑起来。

与 Runtime 的关系​

Runtime 中的 NineClaw-WebSearch 插件把 WebSearch 能力注册给 Hermes：

工具对应能力
nineclaw_search调用 WebSearch 的搜索接口，返回多信源融合后的结果
nineclaw_extract对具体 URL 抽取正文，适合在搜索后核实细节
nineclaw_extract_listlink从列表页或栏目页发现更多相关链接
web_search provider让 Hermes 原有的 web_search 调度可以使用 NineClaw WebSearch 后端

这样，Agent 不需要关心某个信源背后是企业搜索、Wiki、业务 API 还是离线镜像。它只需要调用统一工具，先搜索，再抽取，再把证据用于回答或后续任务规划。

离线环境下的接入方式​

在离线部署中，信源管理通常按以下思路落地：

  1. 用户准备一个内部可访问的信息入口，例如内网搜索 URL、业务系统查询接口或离线网页服务。
  2. 在 WebUI 中创建信源，填写请求方法、查询参数、Header、Body 和代理配置。
  3. 使用代理请求功能确认目标系统能返回 HTML 或 JSON/HTML 页面。
  4. 通过 AI 生成或手工编写 extract(html)，把返回内容转换成标准搜索结果。
  5. 在沙箱中运行提取器，确认每条结果都有 url、title，必要时补充 desc。
  6. 验证通过后启用信源。
  7. Runtime 中的 Agent 通过 WebSearch 工具使用这些内部信源。

这种方式的优点是接入成本低：只要目标系统能被 HTTP 请求访问，并且能从响应中提取链接与标题，就可以纳入 NineClaw 的信息发现链路。

与知识问答的区别​

信源管理和知识问答都服务于“让回答有依据”，但定位不同：

能力更适合的场景
知识问答已上传、已解析、需要稳定召回和重排的正式文档
信源管理分散在多个系统、需要临时搜索、需要访问最新或动态页面的信息

在复杂任务中，两者可以配合使用：先用 QY-RAG 查正式文档证据，再用 WebSearch 补充动态信息；或者先用 WebSearch 发现相关页面，再对关键 URL 做正文抽取。

设计收益​

信源管理让 NineClaw 在离线环境中仍然保留“搜索型智能”的能力：

收益说明
保留 Hermes 的工具优势Agent 可以继续通过搜索发现信息，而不是只依赖模型记忆
快速接入内部系统通过请求配置和提取器适配各类内网信息源
多源汇聚多个信源可并发查询、去重、融合排序
可调试可验证从请求调试到提取器沙箱运行都有明确闭环
可独立扩展搜索执行压力集中在 WebSearch 服务中，可独立扩容和优化

最终效果是：离线部署并不意味着信息能力退化为静态知识库。NineClaw 可以把用户已有的信息系统变成 Agent 可使用的搜索工具，从而继续支撑复杂任务中的信息发现、证据补充和结果核验。
