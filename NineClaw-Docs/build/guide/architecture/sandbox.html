SandBox

沙箱是 NineClaw 在离线环境中运行代码和工具依赖的执行环境。它的意义不是替代 Runtime，也不是把所有依赖都塞进 NineClaw 主系统，而是给业务方一个可以按需打包、按需运行、和主系统解耦的代码执行环境。

简单说：NineClaw 主系统负责管理和调度，沙箱负责承载某次代码执行需要的依赖环境。

为什么需要沙箱​

很多业务能力不是只靠大模型就能完成。实际项目里经常会遇到这些情况：

场景需要沙箱的原因
Skill 依赖特定 Python 包例如解析网页、处理 Excel、访问特定 SDK，主系统不应该为每个 Skill 安装所有依赖
项目依赖特定工具业务方可能需要命令行工具、行业库、内部 SDK 或特定版本运行环境
离线环境不能临时安装包部署后没有公网，运行时缺包就无法临时 pip install
业务依赖变化频繁业务侧工具包变化不应该要求 NineClaw-Manager 或 Runtime 跟着重构发布
不可信代码需要隔离提取器、脚本、调试代码不应该直接跑在 Manager 主进程里

因此，沙箱承担的是“业务代码执行环境”这层职责。它把业务依赖和主系统依赖分开，避免业务方为了一个工具包改动整个 NineClaw 系统。

架构位置​

沙箱相关能力由两部分组成：

组件作用
opensandbox-server沙箱执行服务，负责接收 Manager 的执行请求，并按指定镜像创建隔离执行环境
nineclaw-sandbox:latest实际用于运行代码的沙箱镜像，里面可以预装业务代码需要的 Python 包、系统库或工具

Manager 不直接在自己的容器里执行用户代码。需要运行提取器或脚本时，Manager 调用 OpenSandbox，由 OpenSandbox 使用配置中的沙箱镜像创建临时执行环境。

默认配置中，Manager 通过以下环境变量指定沙箱执行镜像：

OPEN_SANDBOX_IMAGE=nineclaw-sandbox:latest

这意味着业务方可以在不改 Manager 的情况下，重新打包 nineclaw-sandbox:latest，让沙箱拥有新的依赖。

和 NineClaw 主系统的解耦​

沙箱和 NineClaw 主系统是解耦的：

主系统沙箱
负责 WebUI、Manager、Runtime、RAG、WebSearch、部署和接口管理负责某次代码执行需要的依赖环境
版本迭代由 NineClaw 研发节奏控制镜像内容可以由业务方按项目需求维护
不应该频繁因为业务依赖变化而重发版可以因为业务包、工具包、SDK 变化单独重建
关注平台稳定性关注业务代码能否在离线环境中跑起来

这种解耦很重要。离线环境里，业务方经常会发现某个 Skill 或项目脚本缺少依赖。如果依赖必须装进 Manager 或 Runtime，平台会变得越来越重，升级也越来越困难。沙箱把这个问题隔离出来：业务方需要什么包，就打进自己的沙箱镜像里。

离线环境下怎么使用​

典型流程是：

  1. 业务方确认 Skill、提取器或项目脚本需要哪些依赖。
  2. 在沙箱构建文件中加入依赖，例如 Python 包、系统库、内部 SDK 或命令行工具。
  3. 构建新的 nineclaw-sandbox:latest 镜像。
  4. 在离线交付包中带上这个镜像。
  5. 部署后 Manager 仍然通过 OPEN_SANDBOX_IMAGE 使用该镜像。
  6. 业务代码在沙箱里运行，NineClaw 主系统不需要因为依赖变化重新发布。

如果只是补 Python 包，通常可以在 docker/sandbox-requirements.txt 中追加依赖后重新构建沙箱镜像；如果需要系统库或命令行工具，则修改 docker/sandbox.Dockerfile 后重新构建。

和 Skill 的关系​

Skill 描述的是“这个能力怎么被智能体理解和调用”，沙箱解决的是“这个能力运行时需要什么环境”。

举例来说，一个 Skill 可能需要：

Skill 需要沙箱提供
读取 Excel预装 Excel 解析库
调用内部 SDK预装业务方内部 SDK
解析网页预装 HTML 解析、HTTP 请求、清洗工具
运行脚本提供脚本依赖的 Python 包或系统命令

这样 Skill 可以保持轻量，只描述能力和调用方式；真正复杂的依赖放在沙箱镜像里维护。

和 WebSearch 的关系​

信源管理中，用户可能需要编写网页结果提取器。提取器代码不适合直接在 Manager 主进程中执行，因此可以放到沙箱里运行和验证。

这带来两个好处：

好处说明
隔离风险提取器代码出错，不会拖垮 Manager 主服务
依赖可控提取器需要的解析库可以打进沙箱镜像，而不是污染主系统

因此，在 WebSearch 场景中，沙箱更像“提取器调试和验证环境”。

边界说明​

沙箱不负责以下事情：

不负责原因
不负责管理 Runtime 生命周期Runtime 容器由 Manager 管理
不负责知识库召回和重排这是 QY-RAG 的职责
不负责搜索聚合和排序这是 WebSearch 的职责
不负责保存业务配置配置和状态仍由 Manager 和数据库维护
不替代正式业务服务沙箱适合执行代码片段、提取器、工具脚本等，不适合作为长期业务服务入口

沙箱的核心价值是：让业务代码和依赖能在离线环境中运行，同时不把 NineClaw 主系统变成一个不断膨胀的依赖集合。
