产品介绍

NineClaw 是面向组织的 AI 集成与运行平台。它不试图重新发明每一个底层能力，而是把成熟的开源项目、模型能力、知识库能力、搜索能力、运行时能力和部署能力整合到一套可管理、可扩展、可二次开发的平台中。

NineClaw 的核心定位可以概括为一句话：让组织在不丢弃已有资产的前提下，把 AI 能力稳定嵌入自己的业务系统。

产品定位​

NineClaw 面向的不是单个用户的对话体验，而是组织级 AI 能力建设。组织在引入 AI 时，通常会遇到几个现实问题：

问题说明
工具分散模型、RAG、搜索、Agent、部署和管理工具来自不同项目，协议和入口不统一
迁移成本高客户已经积累的数据、配置、工作流和系统接口不能轻易废弃
封闭绑定风险组织不希望关键 AI 能力被单一厂商或单一平台深度锁定
交付环境复杂很多场景需要离线部署、内网运行、私有模型和内部数据源接入
二次开发困难对话界面不能覆盖所有业务能力，很多能力需要 API、SDK 和系统级集成

NineClaw 解决这些问题的方式，不是做一个封闭的“全家桶”，而是做一个开放的集成平台。好的能力可以接进来，已有资产可以继续用，组织可以按需组合，而不是被迫从零迁移到另一套体系。

面向人群​

NineClaw 的核心用户不是单一角色，而是围绕组织级 AI 应用建设形成的一组协作人群。不同人群关注的问题不同，平台提供的价值也不同。

人群关注点NineClaw 提供的价值
驻场研发同事长期处于内网环境，技术共享不足，容易重复建设知识库、接口适配、工具调用等共性能力提供通用接口、可复用组件、运行时能力和参考实现，减少重复造轮子，让研发精力回到客户核心业务问题上
客户业务人员不清楚 AI 能做什么，也难以把前沿技术和具体业务流程联系起来通过统一 WebUI、知识问答、搜索、工具调用和智能体能力，让客户能实际试用、理解能力边界，并启发新业务场景
客户管理者关心效果、风险、成本、交付可控性，以及是否会被单一厂商绑定支持离线部署、私有化接入、组件可替换和多厂商协作，降低组织采用 AI 平台的决策阻力
合作厂商希望把自研能力接入客户现场，但缺少统一入口和标准规范通过 MCP、Skill、API 和标准接入方式，把外部能力纳入平台，共同完善客户侧生态

这也决定了 NineClaw 的边界：它不是某个垂直业务的最终系统，而是帮助不同团队更快做出业务系统的支撑平台。NineClaw 提供的是“厨具”和“标准厨房”，让研发同事、客户团队和合作厂商能更快做出适合业务现场的应用。

为什么基于成熟开源项目改造​

AI 工具生态已经非常丰富。知识库、Agent、运行时、搜索、容器化和前端管理等方向，都有成熟项目和实践经验。如果从零开始重写所有底层能力，团队会把大量精力消耗在重复造轮子和修复底层问题上。

NineClaw 的策略是：尽量不重复造底层能力，把精力集中在集成、适配、管理和标准化上。

这带来几个直接收益：

收益说明
交付更快成熟能力接入后即可形成可用产品，不必等待底层能力从零成熟
稳定性更好复用已经被验证过的开源项目，减少自研底层带来的不确定性
研发聚焦团队把精力放在接口适配、能力编排、部署交付和用户体验上
扩展性更强后续可以继续接入新的模型、RAG、搜索、MCP、Skill 或运行时能力

因此，NineClaw 的价值不在于“所有东西都自己写”，而在于把分散的优秀能力组织成一套可落地的平台。

开放集成，而不是封闭全家桶​

大厂产品通常会走向封闭全家桶：模型、知识库、Agent、工作流、插件市场和运维体系都由同一平台提供。这对个人用户可能足够方便，但对组织而言，风险和成本都更高。

组织更关心的是：

  1. 能不能接入已有系统。
  2. 能不能继续使用已有数据和流程。
  3. 能不能替换某个组件而不影响整体平台。
  4. 能不能在内网或离线环境中稳定运行。
  5. 能不能避免被单一供应商深度绑定。

NineClaw 的平台形态更像一个“能力插座”。用户可以按需接入模型、知识库、搜索源、Skill、MCP Server 和运行时实例。某个组件需要替换时，不必推倒整套系统。

这种开放集成模式降低了组织采用 AI 平台的决策门槛：不要求客户丢弃既有积累，也不要求客户一次性接受完整封闭体系。

面向服务二开​

NineClaw 不把产品重心放在“对话编排”上。对话、Prompt 编排、拖拽式工作流都有价值，但它们不能覆盖所有业务场景。

组织中的很多能力天然不是聊天形态：

场景更合适的形态
审批流后端服务、状态机、业务系统回调
数据同步定时任务、API、消息队列
自动化脚本CLI、Runtime 工具、容器任务
系统集成API、SDK、内部网关
业务查询服务接口、数据库检索、内部搜索

因此，NineClaw 更强调 API、SDK、容器接口和运行时接口。它面向的是希望把 AI 嵌入业务系统的开发者和工程团队，而不是只在聊天窗口里使用 AI 的最终用户。

这个定位决定了 NineClaw 的产品能力要能被程序化调用、能被部署系统管理、能被现有业务系统集成，也能被前端管理界面统一配置。

标准接口是长期壁垒​

集成平台是第一步，但真正有长期价值的是标准接口规范。

不同项目、不同团队、不同开源组件往往有自己的协议、配置方式和调用习惯。如果每个项目都单独适配，最终会形成大量重复工作，能力之间也难以复用。

NineClaw 在接入这些组件时，会逐步沉淀统一规范：

标准化方向说明
模型供应商接口用统一方式管理 OpenAI 兼容模型、私有模型和推理服务
Runtime 管理接口用统一方式创建、启动、停止和访问运行时实例
Skill 规范用统一结构描述技能、说明、脚本、参考资料和运行边界
MCP 接入规范用统一方式管理 MCP Server 的注册、配置和部署
RAG 适配接口用统一方式接入知识库、文档、切片、召回和问答能力
WebSearch 接口用统一方式接入内外部搜索源、详情抽取和列表链接发现
部署交付规范用统一部署包、镜像和 Compose 配置支撑离线交付

一旦标准接口稳定下来，新项目就不需要重复搭建底座。它可以直接复用 NineClaw 的管理、部署、运行时、搜索和知识库能力，把精力集中在业务创新上。

这也是 NineClaw 生态化的基础：项目越多，标准越有价值；标准越稳定，新项目接入成本越低。

多智能体协同​

在完成基础集成后，NineClaw 的重点会逐步转向多智能体协同。

多智能体协同不是简单地增加几个 Agent，也不是在界面上多画几条连线。它关心的是更底层的问题：

问题说明
任务分配一个复杂目标应该拆给哪些 Agent 或工具执行
能力路由不同模型、Skill、MCP、RAG、WebSearch 应该在什么条件下被调用
冲突处理多个 Agent 得到不同结论时，如何验证和收敛
上下文管理如何在多轮、多工具、多来源证据中保持任务一致性
结果审查如何判断信息是否充分、回答是否可靠、操作是否可执行

NineClaw 的优势在于，它不是只控制一个聊天窗口，而是同时掌握模型、Runtime、Skill、MCP、RAG、WebSearch 和部署系统的接口。多智能体协同可以建立在这些统一接口之上，而不是停留在单一对话产品内部。

客户已有资产是基础​

很多组织在引入 NineClaw 前，已经有了自己的数据、知识库、脚本、搜索系统、业务接口和开源项目积累。这些积累不应该被视为迁移包袱，而应该被视为平台建设的基础资产。

NineClaw 的接入思路是：

  1. 已经存在的系统尽量保留。
  2. 能通过接口调用的能力优先接入。
  3. 能通过容器运行的能力纳入部署体系。
  4. 能通过 Skill 或 MCP 表达的能力交给 Runtime 使用。
  5. 能通过搜索入口访问的信息源纳入 WebSearch。
  6. 能作为正式文档沉淀的材料接入 QY-RAG。

这种方式降低了迁移成本，也降低了采购和推广阻力。用户不需要先放弃原有系统，才能开始使用 NineClaw。

产品价值​

NineClaw 的差异不在某个单点功能，而在整套产品逻辑：

方向NineClaw 的选择
底层能力基于成熟开源项目改造，减少重复造轮子
平台形态开放集成，按需接入，而不是封闭全家桶
服务对象面向驻场研发、客户业务人员、客户管理者和合作厂商，支持二次开发和系统集成
交付方式支持容器化、离线部署和局部服务更新
能力沉淀通过标准接口规范提升项目之间的复用性
智能方向在统一接口之上发展多智能体协同
客户资产接入和复用已有积累，而不是要求从零迁移

最终，NineClaw 要解决的不是“再做一个 AI 对话工具”，而是帮助组织把 AI 能力变成可部署、可管理、可扩展、可复用的基础设施。
